# チューニングの手引き（調整の第一候補の定数と、調整時に考慮すること）

2026-10-09 作成（ユーザー指示）。本番で状況を確認しながら数値を弄る試行錯誤の段階にあるので、
**どの値を真っ先に触るか・今の値の意味・変えるときの手順と副作用**をここにまとめる。
経緯と実測の詳細は `docs/design-notes.md`（節番号で参照）、残タスクは `TODO.md`、作業ルールは `CLAUDE.md`。

---

## 0. 値を変えるときの共通手順

1. **選択肢を提示して確定してから着手**（CLAUDE.md）。値はすべてユーザーが決めた定数。
2. **実測してから決める**。各定数の「測り方」の列のスクリプトを `npx tsx scripts/...` で回す
   （環境変数で候補値を差し替えられるものが多い）。結果は設計ノートに表で残す。
3. **Map の評価の意味が変わる値**（1 節の ★）を変えたら `EVAL_VERSION`（`src/app/board/persistence.ts`）を上げる。
   検索結果は別バケツに貯まり、旧バージョンの候補は「コピー」で現バージョンの評価に作り直して引き継げる。
   **List / Total だけに効く値**（船の相互作用）と**表示だけの値**（マーカー）は上げなくてよい。
4. **回帰スナップショット**（`scripts/__snapshots__/baseline.json`、LF テンプレ 150 盤面）は `npm run snapshot:update`
   → 差分が意図どおり（placement / hard 不変、soft だけ）か目視 → 同一コミット。
   基本版テンプレの変化と、色の代表にならない種族の変化は拾わない（3 節）。
5. **版**: 本番へ出すときは `package.json` の version を上げる（評価の意味が変わる・機能追加は 2 桁目、表示や
   ドキュメントだけなら 3 桁目）。FF push 後に同じ番号のタグを `main` に打つ。
6. 毎コミット `npm run typecheck`（0）/ `npm run lint`（エラー 0）/ `npm test`（全緑）。
7. 設計判断と実測を `docs/design-notes.md` に追記し、この手引きの「現在値」を更新する。

### 1-1 / 1-2 の式（いまの実装）

```
T_{s,f}   ＝ 船 s に乗るタイル（基本技術・金枠同盟。アーティファクトはトワイライト）の種族 f の値 × lfShip 係数 / SETUP_SCORE_DIVISOR
C_{s,f}   ＝ Σ_{船 s から scoutRadius 以内の惑星 p} min(1, w_f(p)) × 船接触の値(p)        w_f ＝ eval_v7 の到達係数
C̄_f      ＝ 使う船（result.ships、無ければ 4 隻）の C_{s,f} の平均
rel_{s,f} ＝ (C_{s,f} − C̄_f) / C̄_f                 Σ_s rel ＝ 0 なので全船同じ T なら総和は変わらない
加点_f    ＝ Σ_s α × rel_{s,f} × T_{s,f}            List のセット提案の採点と Total の Setup 列に足す。検索には入れない
```

byFaction を持たない古い候補（eval_v6 以前）は全種族共通の C_s に後退する。基本版（船なし）は加点 0。

## 3. 調整時に考慮すること —— これまでの試行錯誤の教訓

- **係数の方向を言葉で取り違えない**（設計ノート 2.7）。「次元横断に大きく係数をかけて」は「大きく削る」の意味だった。
  係数は 0〜1 の**削る量**（1 ＝ 削らない）として話し、候補値は必ず数字で確認する。
- **「端が有利」は測り方の誤りだった**（設計ノート 2.10）。全種族を混ぜて重心距離と相関を取ると、開始地点の数の違いが
  交絡して符号が反転した。種族ごとに平均を引いてから欠けマス数と相関を取ると端は一貫して不利（−0.41）。
  **新しい傾向を見つけたら、まず測り方を疑う**。
- **二重計上を避ける**（設計ノート 2.7「二重計上」）。ガイア近接の軸 × 入植先、星系の軸 × 固有値の二重計上を eval_v7 で
  一本化した。新しい軸を足すときは、その価値が既存の式（固有値・状況の値・到達係数）にもう含まれていないか確認する。
- **ガイア近接 5 / 8 / 3 のような「由来の分からない値」は調べて、根拠が無ければ捨てる**。2026-07-30 の割合合わせの副産物で
  価値基準に基づかない値だった。
- **尺度が効かないときは係数を上げる前に尺度を疑う**（2026-10-08）。船の相互作用は α を 0.5 → 1 にしても加点が 0.2% → 0.4%
  にしかならず、原因は船どうしの船接触の差が小さい尺度にあった。種族ごとの船接触に変えると α 1 で 2.5% になった。
- **色の代表値は入れ替わる**。ダー・シュワーム人 × 1.5 で赤の代表がハッシュ・ホラ人から替わる盤面があり、
  `evaluateSoft.startAccess.test.ts` の期待値が変わった。種族の値を変えたら代表の入れ替わりを前提にテストを読む。
- **回帰スナップショットは万能ではない**。LF テンプレ 150 盤面だけで、基本版の変化と、色の代表にならない種族の変化は
  差分に出ない（ダー・シュワーム人 × 1.5 は差分なしだった）。`_probe_map_values.ts` で種族の値を直接見る。
- **体感と合わないときは、まず検索条件を確認する**。「端寄りの開始地点が高い気がする」の原因は、欠けマス罰点 0 で
  検索していたことだった（2026-10-08）。
- **「揃っているか」を測るときは、揃わない条件が実際に含まれているか先に確かめる**（CLAUDE.md）。
- **既定値を変えると結果バケツが新しくなる**。評価指数の既定値（`wRimGap` など）は検索キーに入るので、式が同じでも
  既定条件の結果は別バケツになる。保存キーは「無効時フィールド省略」で既存キーをバイト不変に保つ。
- **評価の桁の約束**（設計ノート 1.2）: Map の色ごとの値も Setup の種族ごとの値も 100 前後、足して 200 前後。
  Map の値を変えるときは Setup との合算比（1-8）とセットで考える。
- **本番の確認**: ビルド完了は共通バー右端の「vX.Y.Z · eval_vN」で判定（Etag では判定できない）。狭い幅の見た目は本番で測る。
  埋め込みブラウザにはピン留めマップ・保存セットアップが無いので、List / Total の実データ確認はユーザーに依頼する。
